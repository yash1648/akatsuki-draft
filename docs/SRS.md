# Software Requirements Specification (SRS)

**Project Name:** Akatsuki’s Draft — AI-Enabled Content Sharing Platform  
**Version:** 1.0  

---

## 1. Introduction

### 1.1 Purpose
This document specifies the functional and non-functional requirements for **Akatsuki’s Draft**, a web-based content creation and publishing platform. It is intended for developers, testers, and stakeholders to guide the implementation of the backend API, database architecture, authentication workflows, and AI integration.

### 1.2 Scope
Akatsuki’s Draft allows users to write, manage, and publish articles or posts. Key capabilities include:
* Role-based access control (`user` and `admin`) secured via JSON Web Tokens (JWT).
* Draft management and non-destructive AI content enhancement (generating a new draft document while preserving the original).
* A moderated publishing workflow where user-submitted posts require administrator approval before becoming publicly visible.

### 1.3 Definitions & Acronyms
* **JWT:** JSON Web Token, used for stateless authentication.
* **RBAC:** Role-Based Access Control.
* **CRUD:** Create, Read, Update, Delete.
* **Draft:** A post saved by a user that is not yet submitted for admin review or public viewing.

## 2. Overall Description

### 2.1 User Classes and Characteristics
| User Role | Responsibilities & Permissions |
| :--- | :--- |
| **Guest (Unauthenticated)** | Can register, log in, and view publicly approved posts (`GET /posts`, `GET /posts/:id`). |
| **User (`role: "user"`)** | All Guest permissions, plus: create drafts/posts, edit or delete their own posts, trigger AI improvements on their own posts, and view all of their own posts across any status. |
| **Admin (`role: "admin"`)** | All User permissions, plus: view all pending posts across the platform and transition post statuses to `approved` or `rejected`. |

### 2.2 Operating Environment
* **Database:** MongoDB (NoSQL document storage).
* **Authentication:** Stateless JWT passed via HTTP `Authorization: Bearer <token>` header.
* **External Services:** LLM / Generative AI API (e.g., Gemini, OpenAI) for text enhancement.
* **API Format:** RESTful JSON over HTTPS.

### 2.3 Post Status Lifecycle
A post moves through four distinct states:
1. **`draft`**: Initial private state when saved without submitting, or when generated by the AI improvement endpoint.
2. **`pending`**: Submitted by the author for administrator review.
3. **`approved`**: Reviewed and accepted by an admin; publicly visible to all users.
4. **`rejected`**: Reviewed and declined by an admin; visible only to the author (and admins).

## 4. Functional Requirements & API Specifications

### 4.1 Authentication Module

| Endpoint | Method | Auth | Request Body / Params | Success Response | Error Cases |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `/auth/register` | `POST` | Public | `{ name, email, password }` | `201 Created` — User object (excluding password). | `400` Validation error<br>`409` Email already exists |
| `/auth/login` | `POST` | Public | `{ email, password }` | `200 OK` — `{ token, user: { id, name, email, role } }` | `401` Invalid credentials |
| `/auth/me` | `GET` | User / Admin | Header: `Authorization: Bearer <token>` | `200 OK` — Current user's profile (excluding password). | `401` Missing or invalid token |

* **FR-AUTH-1:** Passwords must be hashed using `bcrypt` (minimum 10 salt rounds) before saving to MongoDB.
* **FR-AUTH-2:** Public registration (`POST /auth/register`) must strictly assign `role: "user"` regardless of whether a `role` field is passed in the request body, preventing privilege escalation.

### 4.2 User Post Management Module

| Endpoint | Method | Auth | Request Body / Params | Success Response | Error Cases |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `/posts` | `POST` | User / Admin | `{ title, description, content, image, category, status? }` | `201 Created` — Created post document. | `400` Invalid fields or disallowed status |
| `/posts` | `GET` | Public | Optional Query: `?category=&page=&limit=` | `200 OK` — Array of posts where `status === "approved"`. | `500` Server error |
| `/posts/:id` | `GET` | Public | Param: `id` (Post ObjectId) | `200 OK` — Single post where `status === "approved"`. | `404` Post not found or not approved |
| `/posts/my-posts` | `GET` | User / Admin | Optional Query: `?status=` | `200 OK` — Array of posts where `createdBy === req.user.id`. | `401` Unauthorized |
| `/posts/:id` | `PATCH` | User / Admin (Owner only) | Param: `id`<br>Body: Partial post fields | `200 OK` — Updated post document. | `403` Not the owner<br>`404` Post not found |
| `/posts/:id` | `DELETE` | User / Admin (Owner only) | Param: `id` | `200 OK` — Confirmation message. | `403` Not the owner<br>`404` Post not found |

* **FR-POST-1 (Creation Status Constraint):** When creating or updating a post via `/posts`, standard users may only set `status` to `"draft"` or `"pending"`. Any attempt by a non-admin to pass `status: "approved"` or `"rejected"` must be rejected with `403 Forbidden` or coerced to `"pending"`.
* **FR-POST-2 (Edit Reset Rule):** If a user updates (`PATCH /posts/:id`) a post that is currently `"approved"` or `"rejected"`, its status must automatically revert to `"draft"` or `"pending"` (depending on user action) so unreviewed edits cannot go live directly.
* **FR-POST-3 (Route Ordering):** In the router implementation (e.g., Express.js), `GET /posts/my-posts` must be declared **before** `GET /posts/:id` so `"my-posts"` is not interpreted as a `:id` parameter.

### 4.3 Admin Moderation Module

| Endpoint | Method | Auth | Request Params | Success Response | Error Cases |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `/admin/posts/pending` | `GET` | Admin only | Optional Query: `?page=&limit=` | `200 OK` — Array of posts with `status === "pending"`. | `401` Unauthorized<br>`403` Admin role required |
| `/admin/posts/approve/:id` | `PATCH` | Admin only | Param: `id` (Post ObjectId) | `200 OK` — Post updated to `status: "approved"`. | `400` Post is not in `pending` state<br>`403` Forbidden<br>`404` Not found |
| `/admin/posts/reject/:id` | `PATCH` | Admin only | Param: `id` (Post ObjectId) | `200 OK` — Post updated to `status: "rejected"`. | `400` Post is not in `pending` state<br>`403` Forbidden<br>`404` Not found |

* **FR-ADMIN-1:** Only posts with `status: "pending"` can be approved or rejected. Admins cannot directly approve a private `"draft"` that a user has not submitted.

### 4.4 AI Content Improvement Module

| Endpoint | Method | Auth | Request Params / Body | Success Response | Error Cases |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `/ai/improve/:postId` | `POST` | User / Admin (Owner only) | Param: `postId` | `201 Created` — Newly created draft post containing AI-improved content. | `403` User does not own original post<br>`404` Original post not found<br>`502` AI provider failure |

* **FR-AI-1 (Non-Destructive Versioning):** Calling `POST /ai/improve/:postId` must **never** mutate the source document (`:postId`).
* **FR-AI-2 (Cloning & Saving):** The system must:
  1. Fetch the source post and verify `post.createdBy === req.user.id`.
  2. Send `title`, `description`, and `content` to the configured AI service with a system prompt instructing it to improve clarity, grammar, flow, and engagement while preserving the author's core meaning.
  3. Insert a **new** `Post` document in MongoDB with a newly generated `_id`, the AI-refined `title`/`description`/`content`, copied `image` and `category` from the original, `createdBy` set to `req.user.id`, and `status` strictly set to `"draft"`.
  4. Return the newly created draft document to the client.

## 5. Non-Functional Requirements (NFRs)

### 5.1 Security
* **NFR-SEC-1 (JWT Expiration):** JWTs must include an expiration claim (`exp`), recommended at `24h` or `7d`, signed with a strong secret (`HS256`).
* **NFR-SEC-2 (Input Sanitization):** All user inputs (`content`, `title`, `description`) must be sanitized against NoSQL injection (e.g., stripping `$` keys in MongoDB queries) and XSS payloads before rendering.
* **NFR-SEC-3 (Rate Limiting):** Apply strict rate limiting on `/auth/*` (to prevent brute-force attacks) and `/ai/improve/:postId` (e.g., max 10 requests per user per hour to prevent LLM API quota exhaustion and cost spikes).

### 5.2 Performance & Reliability
* **NFR-PERF-1 (Database Indexing):** Create compound indexes on `{ status: 1, createdAt: -1 }` for fast public feed queries (`GET /posts`) and `{ createdBy: 1, createdAt: -1 }` for `/posts/my-posts`.
* **NFR-PERF-2 (AI Timeouts):** AI improvement requests must have an explicit timeout (e.g., 30 seconds) and graceful error handling (`502 Bad Gateway` or `504 Gateway Timeout`) if the upstream LLM provider fails, ensuring no partial/corrupted drafts are saved.

## 6. Architectural Recommendations & Edge Cases

1. **Viewing Non-Approved Own Posts by ID (`GET /posts/:id`):** If `GET /posts/:id` strictly filters for `status: "approved"`, an author clicking on one of their own drafts to open it in an editor will receive a `404`. Consider allowing `GET /posts/:id` to return non-approved posts if the requester provides a valid JWT matching `post.createdBy` or has `role: "admin"`.
2. **Linking AI Drafts to Originals:** Adding an optional `parentPostId: { type: ObjectId, ref: "Post", default: null }` field to the `Post` schema allows the UI to link AI-improved drafts back to the original draft.
3. **Rejection Feedback:** Adding an optional `rejectionReason: String` field when an admin calls `PATCH /admin/posts/reject/:id` helps authors understand what to fix before resubmitting.
4. **Updated Timestamp:** Enabling Mongoose `{ timestamps: true }` to automatically track `updatedAt` alongside `createdAt` helps users sort their drafts by most recently edited.
